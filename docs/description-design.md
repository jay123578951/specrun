# Skill description 設計原則

> **性質**：kit repo 的維護規範。**不進 plugin 出貨、不被 runtime 載入。**
>
> **用途**：要改任何 skill 的 `description` 時先讀這份，改完拿 `routing-cases.md` 對答案。兩份配對使用：這份管「怎麼寫」，考卷管「寫完怎麼驗」。
>
> **來源**：2026-08-19 一輪 description 重寫（`feat` / `fix` / `decisions`）中沉澱，每條都附當時的實證。**這份文件會長大**：日後每次改 description 若學到新東西，補一條並附證據。

---

## 前提：description 是路由器的唯一輸入

模型選 skill 時，手上只有各 skill 的 `name + description` 並排。**沒有任何一份 SKILL.md 內文在那個當下被載入。** 這句話決定了下面每一條原則。

它同時意味著兩件事：

- description 裡放不進判準的東西（執行前提、操作步驟、機制說明）是純成本。
- 內文寫得再好，也救不了 description 的誤導。內文只在「已經選對」之後才生效。

---

## 一、判準要指向事實，不要指向結論

一份 description 可以做兩種很不一樣的事：

- **A 型：告訴模型該得出什麼結論。** 「5+ 檔 → feat」。這是查表。
- **B 型：告訴模型該看哪個事實。** 「看模組邊界有沒有移位」。這不取代判斷，是把判斷瞄準。

**寫 B 型。** A 型要賭你窮舉得完案例，賭輸的方式是在沒預料到的案例上明確地錯；B 型不用賭，因為推論仍在模型手上。

判斷放權或指定時，三問：

1. 這個判斷需要的是**通用知識**還是**本專案約定**？知識放權（模型讀過的 Vue 比 description 多），約定要寫（訓練資料裡沒有事實可查，模型只能挑一個合理值，而合理值不只一個）。
2. **判錯了會不會有東西叫？** 不會叫的要寫。
3. 我要寫的是「看哪裡」還是「得什麼結論」？是結論就改寫成「看哪裡」。

**實證**：`feat` 原本寫「大型重構」。大小是連續量，模型只能估。換成「改變模組邊界的重構（抽出共用介面、調整依賴方向）」之後，同一題（重構 stores 目錄抽共用 util）的判對理由從「五個 store 已超出小型模組微調」（語意推理）變成「抽出共用 util 即 description 明列的模組邊界重構」（引明文）。

**推論**：給理由比給規則好。`feat` 的「新增 API/元件」補上「介面契約本身即規格，與行為簡繁無關」之後，模型不只答對了 health endpoint 那題，還能外推到沒列舉的案例（新增一個 CLI flag 算不算、新增一個 event 算不算）。只有規則就得猜，有理由就推得動。

---

## 二、曖昧不必消滅，但不能改變答案

自然語言消不掉模糊。追求「寫到完全不曖昧」會把 description 推向查表，也就是推回 A 型。

**該量的不是「有沒有模糊詞」，是「這個模糊詞的兩種讀法會不會給出不同去向」。** 會，才是缺陷；不會，就是正常的自然語言。

**檢驗方法要注意**：不能用「這次答對了」當證據，那可能只是猜對。要看考卷 subagent 在「曖昧題」段自述的另一種讀法會導向哪裡。它每次都會寫出來，那就是現成證據。

**推論：模糊會移位，不會歸零。** 換掉一個模糊詞得到的不是「不再模糊」，是「模糊從不可查的量移到可查但需定義的概念」。目標是**把模糊推到邊緣**：核心案例查得動，只有邊緣案例需要判斷。

判準的可判性是梯度，不是二元：

| 判準 | 可查嗎 | 跟真正在乎的事有關嗎 |
|---|---|---|
| 「5+ 檔」 | 可查，零模糊 | **無關**（過擬合） |
| 「大型重構」 | **不可查** | 有關 |
| 「改變模組邊界」 | 核心可查，邊緣殘留 | 有關 |

第三種是對的位置。

## 三、錯法的方向決定要不要修

路由的兩種錯法**不對稱**：

- **往重的方向錯**（該輕流程卻走重的）：使用者立刻有感、會抱怨、會被抓到。**大聲的失敗，可容忍。**
- **往輕的方向錯**（該重流程卻走輕的）：pipeline 一路綠燈，code 也對，只是 spec 庫靜默漏記一條。沒有任何 gate 會叫。**安靜的失敗，不可容忍。**

所以同樣是「會改變答案」的曖昧，危害等級可以差很多。補一句話要付出字數與新風險，換來的若只是防一個會自己叫的錯，不划算。

**實證**：`feat`/`fix` 之間「替換共用層內部實作算不算改變模組邊界」沒寫，誤讀會判成 `feat`（流程過重）。判定不補。而「新增 API 是否無條件觸發 `feat`」誤讀會判成 `fix`（漏記 API surface），判定要補。

**知道什麼時候停**：當所有殘留曖昧都落在「往重的方向錯」或「考題資訊不足」時，就該停。繼續修是報酬遞減，而且每次「再精進一點」的動作本身都可能引入新問題（本輪就發生兩次，見第五條）。

---

## 四、description 只放「幫模型選 skill」的東西

不幫選擇的東西一律歸內文。三類常見的雜訊：

**執行前提。** `feat` 原本寫「前提是已有 OpenSpec change（含 tasks.md）」。它對路由的貢獻是零（不區分 `feat` 和 `fix`，兩個都在 SDD 體系裡），唯一可能的作用是讓模型在前提不滿足時**退選**，那正是最不該發生的誤讀。刪掉，內文（`feat/SKILL.md`）本來就寫了，還寫得更完整。

判斷方式：這句話是**擋門**還是**指路**？擋門的絕不能進 description。純指路的（例如「選了之後要先跑前置流程」）也該歸內文，只是危害等級低。

**分級標籤。** `Tier 2` / `Tier 3` 這類編號，在選用當下沒有定義來源，模型只能從序數推「3 比 2 重」，而那件事後半句判準已經講完了。更糟的是它讓 description 讀起來像在引用一套外部分級體系，暗示真正的判準在別處。用指令名（`/srun:feat`）取代編號：名字本身可執行，讀到即知道要跑什麼，不必先解一次映射。

**正面例子。** 例子會夾帶它自己的隱含判準。`decisions` 寫「存在這種分支時使用（一個就算，完整新功能與全新 UI 流程設計典型如此）」，後半句的「完整新功能」自帶規模暗示，正好稀釋掉同一句裡的「一個就算」。**判準要窄，例子要嘛不加，要嘛加在內文。**

**反例**：`decisions` 的「在 `opsx:explore` 之後、`opsx:propose` 之前」該留。那是**定位**，位置本身就是「什麼時候該選它」的一部分，而且它不擋門。

## 五、從內文概括到 description 時，最容易弄丟限定子句

這是本輪出現頻率最高的失敗模式，三次：

| 位置 | 內文有的 | description 概括成 | 後果 |
|---|---|---|---|
| `fix` 微決策路徑 | 「1-2 個未定小決策」 | 「決策分支多」 | 唯一可查的線索消失 |
| `decisions` 適用判斷 | 「有一個就跑」 | 「決策分支多的任務」 | **門檻被抬高**，單一分支的任務會被判跳過 |
| `decisions` 成立條件 1 | 「存在多種合理實作，**且選哪種會改變使用者看到的行為或資料結構**」 | 只搬前半 | 「grid 還是 flex」照字面會落進「跑」 |

第二個是實質錯誤不是措辭問題：跳過 `decisions` 的後果是模糊在 propose 被包裝成看似完整的 spec，Coder 照跑、gate 照綠，retry 階段才爆。那正是這個 skill 存在的唯一理由被繞過，而且是安靜的失敗。

第三個是寫這份文件的人（我）自己犯的，而且犯在剛批評完前兩個之後。

**做法**：改 description 時，把內文對應段落**逐條並排**看過，特別盯「且」「同時成立」「不算」這類限定與排除語。概括可以簡化措辭，不可以丟掉限定。

---

## 六、判準之間不要並列兩個獨立的軸

兩個軸各自能給出答案而沒說誰優先時，答案卷裡就會出現一條沒寫在任何地方的規則。

**實證**：`feat`/`fix` 原本同時有主判準（決策收斂沒／要不要新 spec artifact，二元可判）和形容詞軸（大型／小型，連續不可判）。「重構 stores 目錄」在主判準上三項全指 `fix`，答案卷卻寫 `feat`，實際上是用形容詞軸覆蓋了主判準，而那條覆蓋規則沒寫。

**做法**：新判準要嘛併入既有軸（「改變模組邊界」就是「架構變更」的細粒度版本），要嘛明寫優先序。並列是最糟的選項。

**推論：描述工作的性質，不要描述某個時間點的狀態。** `feat` 原本寫「決策分支多」，但 `feat` 執行時決策一定已定案（tasks.md 是 propose 的產物），所以那句讀起來像在講 feat 執行時決策還開著，怎麼讀都有一邊講不通。改成「決策收斂成本高（分支彼此相依，一題的答案會改變另一題的選項）」之後，描述的是工作的固有性質，跟看它的時間點無關。

## 驗證方法

改完拿 `routing-cases.md` 對答案。**必須 clean-room**：

- 開一個 fresh-context subagent，**只餵 description 全文與題目**，明令禁止讀取 repo（標準答案在裡面）。
- 自己對答案不算，改動者握著全部 context，會不自覺補完 description 沒寫的東西。
- 要求 subagent 輸出「曖昧題」段，寫出另一種讀法。**那段比答對率更有資訊量**：答對可能是猜對的，曖昧題自述才看得出它是查判準還是自己補。
- 全對才放行。錯誤死在 kit repo，到不了真實開發。

**判嚴重度時要把環境加回來。** 考卷刻意把 description 抽離環境單獨測，那是它的價值，但據此判「這個曖昧有多危險」會高估。真實環境有 SessionStart 意圖引導 hook、有 README、有前置流程。本輪撤掉過一個提案（`feat` 的 openspec 前提補述），就是因為忘了把環境加回來。

**沒有考卷的判準等於沒有回歸網。** `decisions` 的第二層路由（跑不跑）原本無人校準，本輪才補上 B 組 8 題。新增或改動任何影響路由的判準時，同步問一句：這條有考題嗎？

## 待沉澱

- 「要不要進 pipeline」那一層（主對話直改 / 不派發）的判準目前寄生在 `fix` description 末句一句話裡，實際承載者是 SessionStart hook。**四個去向只有兩個有 description**，判準密度不均，殘留曖昧幾乎全部聚在那裡。這一層要不要有自己的規範與考卷，未定。
- 「新增一條 API 就必須走完整 `feat` pipeline」的重量代價（例如一個回傳版本號的 health endpoint）。目前用「spec 完整性優先於流程經濟」解決，是否該有輕量入口，未定。
