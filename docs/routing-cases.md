# 路由回歸案例集（G9）

> **性質**：kit repo 的維護工具——**不進 plugin 出貨、不被 runtime 載入、不直接影響路由**。它是改 description 措辭時的校準基準（考卷）：路由推薦的準確度活在 `feat` / `fix` 的 description 措辭裡，措辭會被改；改完拿本表逐句問模型「這個需求會路由到哪個指令」對答案，**全對才放行**。錯誤死在 kit repo，到不了真實開發。
>
> **配對文件**：`description-design.md` 管「description 怎麼寫」，本份管「寫完怎麼驗」。改 description 前先讀那份。
>
> **維護**：每次動到 `feat` / `fix`（A 組）或 `decisions`（B 組）的 skill description 後掃一遍。retro 迴路（`runs.jsonl`）中出現 G7 規模超標事件＝路由誤判實錘，消化時把誤判實例加為新題——案例集跟實戰長大。
>
> **判準版本**：2026-07 審查第 21 條定案——主判準為「決策狀態」＋「是否需要新的 OpenSpec artifact」；檔案數僅輔助訊號。典型錯誤型態：改寫 description 時只顧新意圖、掉了舊排除條件（如「新增 API/元件 → `feat`」在改寫中遺失 → 新元件被送 `fix` → 一路綠燈但 spec 庫靜默漏記）。

## 案例 A：需求路由（`feat` / `fix` / 直改 / 不派發）

| # | 需求句（canonical） | 預期路由 | 判準依據 |
|---|--------------------|---------|---------|
| 1 | 「做一個使用者資料匯出 CSV 的新功能，含後端 API 與前端下載按鈕」 | `/srun:feat` | 新增 API/元件 → 需 spec 記錄 |
| 2 | 「手機版導覽列在窄螢幕會蓋住內容，修一下（layout 元件＋樣式檔＋一個頁面）」 | `/srun:fix` | 跨檔案 bug 修復、決策明確、不需新 artifact |
| 3 | 「把送出按鈕的文字『送出』改成『儲存』」 | 主對話直改 | 純文案微調 |
| 4 | 「照我們剛剛討論定案的排序邏輯改法做——改兩個 composable 和一個頁面」 | `/srun:fix` | 決策已在對話收斂（場景 i） |
| 5 | 「剛跑完的 change 驗收時發現日期格式顯示錯誤，小修一下」 | `/srun:fix`（場景 ii） | 進行中 change 的驗收修正；不大到重跑 `feat` |
| 6 | 「新增一個可重用的 DatePicker 元件，之後多個表單會用」 | `/srun:feat` | 新增元件 → 需 spec 記錄（即使初期檔案不多） |
| 7 | 「整個結帳流程要重新設計，可能要分幾個階段做」 | `/srun:feat`（先 explore/decisions/propose） | 決策分支多、變更需拆批 |
| 8 | 「卡片之間的間距改成 16px」 | 主對話直改 | 純樣式微調 |
| 9 | 「email 驗證的 regex 漏掉 `+` 號，單一 util 檔改一行」 | 主對話直改 | 單行修正 |
| 10 | 「加入 Google 第三方登入」 | `/srun:feat` | 新功能、需 spec 記錄（且安全敏感） |
| 11 | 「錯誤提示改用既有的 toast 元件顯示——剛剛已討論定案，動三個頁面共用的 error handler」 | `/srun:fix` | 微決策已收斂、沿用既有元件、不需新 artifact |
| 12 | 「重構 stores 目錄，把五個 store 的重複邏輯抽成共用 util」 | `/srun:feat` | 大型重構跨模組＋新增共用介面 |
| 13 | 「加一個 `/api/health` 端點回傳版本資訊，很小的改動」 | `/srun:feat` | **陷阱題**：檔案少但新增 API → 需 spec 記錄；「很小」不是判準 |
| 14 | 「頁面 title 有錯字」 | 主對話直改 | 純文案 |
| 15 | 「這功能要即時更新還是手動刷新？還沒想清楚，先做做看」 | 不派發——先收斂決策（對話釐清；分支多用 `/opsx:explore`＋`/srun:decisions`） | 決策未收斂不進任何 pipeline；收斂後再判路由 |

## 案例 B：`decisions` 跑不跑

> 考的是流程內的第二層路由：已在 `feat` 路線上、`opsx:explore` 之後，這一棒該不該跑。判準取自 `decisions/SKILL.md` 的「核心判準」：待決策分支需**同時**成立「存在多種合理實作（選哪種會改變行為或資料結構）」與「目前沒有明確答案」，**有一個就跑**。

| # | 情境（canonical） | 預期 | 判準依據 |
|---|------------------|------|---------|
| B1 | 「做資料匯出功能：匯出哪些欄位、CSV 還是 Excel、大量資料要不要背景處理，都還沒定」 | 跑 | 多個分支同時命中兩個成立條件 |
| B2 | 「新增訂單列表頁；explore 已定案沿用既有 DataTable、分頁照專案慣例、欄位清單使用者已列出」 | 跳過 | 分支都有明確答案 → 直接 `opsx:propose` |
| B3 | 「密碼重設流程：重設連結有效期多久還沒定，其餘照既有 auth 慣例」 | **跑** | **哨兵題**：只有一個未定分支，但它必須有答案。防「決策分支**多**」的高門檻復辟 |
| B4 | 「新按鈕用專案既有 primary 樣式還是自訂顏色」 | 跳過 | 答案能從既有慣例讀出 → 自己讀，不要問使用者 |
| B5 | 「全新的批次匯入流程：空狀態、部分失敗、重試邊界都還沒設計」 | 跑 | 全新 UI 流程，多個分支影響使用者看到的行為 |
| B6 | 「這個列表內部用 grid 還是 flex 排」 | 跳過 | 純實作風格，不影響行為與資料結構 |
| B7 | 「快取要放記憶體還是 Redis（這份快取供多台機器共享）；專案已有 Redis 且 CLAUDE.md 規定共享狀態一律走 Redis」 | 跳過 | 表面有多種做法，但既有規範已排除其他選項 → 只有一種合理做法 |
| B8 | 「這個看板要即時推播還是手動刷新？（專案目前沒有即時推播基礎建設）」 | 跑 | 單一分支但會改變資料流與架構，Coder 動手前必須有答案 |
