開發項追蹤：大功能拆段開發時，規劃層資訊（切分、順序、動工前必知、否決過的做法）在 change 開出之前的家。roadmap 記**規劃方向**，spec 記**詳細規格**。核心性質：**暫存區，不是存放處**。每則筆記都有保證出口（開 change 遷入 design.md、全交付刪檔），所以它不會長大。

## 啟用與停用

| 磁碟狀態 | 意義 |
| --- | --- |
| `openspec/roadmap/` 存在 | 啟用。目錄即開關，`ls` 即現有開發項清單 |
| `openspec/roadmap.off` 存在 | 使用者已表態這專案不用，永久靜默 |
| 兩者皆無 | 廣告態：討論收斂出多段切分時問一次要不要記錄並啟用 |

啟用＝經使用者同意後建目錄寫入首檔（目錄隨檔案進 git），並順手刪 `roadmap.off`（若有）。停用＝使用者表態後建空檔 `openspec/roadmap.off`。

## 收錄門檻

只收**需要規劃**的開發項。「任一次 change 順手做即可」的小項不收，留在程式碼 `TODO(debt)`；收進來反而給了它一個不會消失的家。

## 檔案配置

一項一檔，檔名用主題 slug（`會員權限管理.md`、`api-版本升級.md`），不設總覽頁。不強制對齊 capability：多數自然對齊，跨切關注點與外部依賴各自成項。

## 檔案格式

兩種形態，不強迫統一：多段項目有拆分表，單段項目沒有（一列的表是噪音）。

**標題行**：`# 名稱` ＋ 右欄，右欄只有三種值：

| 右欄 | 意思 |
| --- | --- |
| 空 | 可以挑 |
| `卡著` | 現在動不了，理由看 `## 開始的條件` |
| `N/M` | 多段項的進度，N>0 表示進行中 |

不區分卡在什麼（等外部、等別項、被裁示暫緩），那是 `## 開始的條件` 的工作，一個詞扛不動也不需要扛。也不標「進行中」：單段項 propose 時就刪檔（見「遷出」），活著的單段項必然還沒開工。

查「接下來開發什麼」時 `grep -h '^# ' openspec/roadmap/*.md` 一次掃完：有 `N/M` 且 N>0 就接那一項的下一段（開檔看 `⬅ 接下來`），沒有就從空右欄裡挑，`卡著` 一律排除。

**標題下的關係欄位**（有才寫，一律附用途註記，不寫裸檔名）：

| 欄位 | 意義 |
| --- | --- |
| `規格` | 對應的 spec 路徑與規模 |
| `為什麼這樣拆` | 指向 archive 的 design.md |
| `前置` | 誰要先完成 |
| `阻斷` | 本項擋住了誰 |
| `順位` | 相對排序 |
| `相關` | 有牽連但無先後的項目 |
| `屬於` | 上層大項檔；本檔全交付 rm 時回該檔拆分表打勾 |

**區塊標題固定四個**，各自回答一個問題：

| 標題 | 回答什麼 | 何時出現 |
| --- | --- | --- |
| `## 開始的條件` | 什麼還沒到位、為什麼還不能動 | 有前置或阻斷時 |
| `## 拆分與進度` | 分成哪幾段、各段做什麼、做到哪 | 只有多段項目 |
| `## 動工前必知` | 開始前得先知道的既有事實與坑 | 幾乎都有 |
| `## 已否決的做法` | 想過但不做的，附理由，免得重想 | 有否決紀錄時 |

子標題帶目的，寫成結論句（`### 一併消失：生命週期綁定 mock 檔案，不需刻意記得`）。

**詞彙**：不設拆分單位名詞。表格欄位用「範圍」、指稱用「本項」，不發明「階段」「切片」這類會撞專案領域詞的單位名。

**範例（多段）**：

~~~markdown
# 會員權限管理        2/6

- **規格**：`specs/member-permission/spec.md`（21 條需求）
- **為什麼這樣拆**：`changes/archive/2026-08-20-member-role-repository/design.md`
- **相關**：`稽核紀錄保存.md`（授權檢查的另一項輸入）

## 拆分與進度

| # | 範圍 | change | 狀態 |
|---|------|--------|------|
| 1 | 角色主檔 | `2026-08-20-member-role-repository` | ✅ |
| 3 | 授權檢查鏈 | — | ⬅ 接下來 |
| 4 | 權限異動稽核 | — | |

## 動工前必知

### 4. 權限異動稽核
- **本項補上「異動來源」，`稽核紀錄保存.md` 補上保存期限**：兩者都到齊，稽核查詢才能改為伺服端強制
~~~

**範例（單段）**：

~~~markdown
# 取得正式環境憑證        卡著

**不是開發工時，是外部資源申請**：專案內無等價來源可換。

- **阻斷**：`api-版本升級.md`（未結清前不得接正式端，理由見該檔「開始的條件」）

## 動工前必知
- 現況：測試端用自簽憑證，**正式端仍是暫代設定**
~~~

## 三層分組（大項檔）

大項目切成多個子項、子項各自還要拆段時，往上加一層：大項一檔，拆分表的列指向**子項檔**而非 change。**結構規則：只有大項檔的列可指檔案，子項檔的列只准指 change**。還想更深＝上層切分過寬，拆成多個大項檔回到平面互聯。

- 大項檔只准放三樣：拆分表、`為什麼這樣拆`、大項層級的已否決做法。子項層的筆記一律寫進子項檔，大項檔不是筆記集散地。
- 子項檔以 `屬於` 欄位回指上層（附用途註記，同關係欄位規則）。
- 還沒想清楚的子項先佔位，子項欄寫「未細分」，想清楚才建檔。
- 標題行 `N/M` ＝ 完成的子項數。`grep -h '^# ' openspec/roadmap/*.md` 一掃同時得到大項與各子項兩層進度。
- **出口鏈**：rm 任何帶 `屬於` 的子項檔前，先回上層檔該列打勾、更新 `N/M`（找不到上層就 `grep -rl` 自己檔名）；勾完子項欄檔名留著，內容在 git。上層全勾 → 照「歸檔更新」的確認規則 rm 大項檔。

**範例（大項檔）**：

~~~markdown
# 會員子選單        1/4

- **為什麼這樣拆**：（切分理由先寫在此，首個 change 的 design.md 產出後改指路徑）

## 拆分與進度

| # | 範圍 | 子項 | 狀態 |
|---|------|------|------|
| 1 | 會員資料維護 | `會員資料維護.md` | ✅ |
| 2 | 權限設定 | `權限設定.md` | ⬅ 接下來 |
| 3 | 匯出報表 | 未細分 | |
~~~

## 寫入

- **建檔**：討論收斂出多段切分、使用者同意記錄時建檔，切分表＋各段動工前必知一次落檔。
- **外溢筆記**：討論產出超出當前 change 範圍的結論 → 問使用者要不要記；記在它**所約束的那一段**底下。筆記的位置就是它的歸屬：同時約束多段就各寫各的、一句互指。
- **禁止全域筆記區**。放不進任何一段的筆記代表三種情況之一：切分切錯（拆開分掛）、它本身是個開發項（另立一檔）、重複記載（刪掉）。
- 跨項關係用標題下的關係欄位表達，不寫成筆記。

## 遷出（propose 時）

本題屬某 roadmap 開發項時，「動工前必知」**整組**遷入新 change 的 design.md，之後：

- **單段項**：整檔 `rm`。存在理由就是那批必知，遷完即空殼；內容在 design.md 與 git 裡。
- **多段項**：該段的必知自 roadmap 刪除，change 名填進拆分表該列，建立雙向連結（歸檔時 grep 得到）。

## 歸檔更新

只有多段項會活到這一步（單段項在 propose 時已刪）。

- `grep -rl "<change 名>" openspec/roadmap/` 找到該列 → 打勾、更新標題行的 `N/M`。
- 最後一段交付 → 確認拆分表全勾、向使用者說一聲，再 `rm` 整檔。刪除是原子操作，歷史在 git。

## 紅線

- **單向依賴**：roadmap 可引用 spec；spec 不得引用 roadmap。規格是行為契約，不該知道專案排程，範圍邊界只寫客觀條件。
- 不記已交付內容、不當 changelog：git 與 archive 就是答案。
- 不重述 design.md 已有的決策，指路徑即可。
